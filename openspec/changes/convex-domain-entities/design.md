# Design: Convex Domain Entities

## Technical Approach

Single `packages/backend/convex/schema.ts` using `defineSchema` + `defineTable` + `v.*` validators.
Config sub-objects (horarios, feriados, pricing) are embedded directly in `Sede` — always co-read, no independent query need.
`Cancha` holds an optional override object; its fields shadow the sede defaults at query time (logic in functions layer, not schema).
Foreign keys use `v.id("tableName")` throughout.
Types are surfaced via `packages/backend/src/index.ts` using Convex's `Doc<"tableName">` and `Id<"tableName">` inference.

## Architecture Decisions

### Decision: Embed horarios/feriados/pricingConfig in Sede

| Option | Tradeoff | Decision |
|--------|----------|----------|
| Embed in `Sede` doc | Always consistent, one fetch, no join | **Chosen** |
| Separate `sedeConfig` table | Extra read per sede load, adds index overhead | Rejected |

Rationale: these objects are small (≤7 day-entries + ≤30 feriados/year), always read together with the sede, and have no independent query requirement.

### Decision: Cancha schedule/pricing as override object (not copy)

| Option | Tradeoff | Decision |
|--------|----------|----------|
| Full copy of schedule + pricing per cancha | Duplication, sync risk | Rejected |
| Optional `v.optional(v.object({...}))` overlay | Null = inherit from sede, explicit = override | **Chosen** |

Rationale: most canchas share the sede's schedule. Copy-on-override keeps storage minimal and makes the inheritance intent self-documenting in the schema.

### Decision: Payment as independent table (not embedded in Reserva)

| Option | Tradeoff | Decision |
|--------|----------|----------|
| Array of payments embedded in `Reserva` | Simple reads, breaks MercadoPago reconciliation | Rejected |
| Separate `payments` table with `reservaId` FK | Supports multiple partial payments, MP transaction IDs | **Chosen** |

Rationale: MercadoPago may issue split transactions; a separate table with `mercadoPagoId` as a unique index prevents duplicate processing.

### Decision: Cliente scoped per Sede (not global User)

| Option | Tradeoff | Decision |
|--------|----------|----------|
| Global `clientes` table linked to `users` | Cross-sede data visible to all dueños | Rejected |
| `clientes` with `sedeId` field | Data isolation per sede, clear ownership | **Chosen** |

Rationale: GDPR-adjacent data isolation — a dueño must only see clients who interacted with their sede.

### Decision: RecurrenceSeries as independent table

| Option | Tradeoff | Decision |
|--------|----------|----------|
| Embed recurrence in `Reserva` | Complicates per-instance cancellations | Rejected |
| Separate `recurrenceSeries` table; `Reserva` has optional `seriesId` | Cancel one instance without mutating the series | **Chosen** |

Rationale: "cancel this instance only" vs "cancel all future" are two distinct operations. Keeping the series intact with per-instance override is standard calendar pattern (RFC 5545 EXDATE).

### Decision: SedeAccess compound index (userId + sedeId)

`SedeAccess` is queried most often as "does this user have access to this sede?" — compound index `by_user_sede` covers this in O(1). Secondary index `by_sede` covers "list all staff of a sede".

## Data Flow

```
apps/web or apps/mobile
        │
        │  import { api } from '@canchero/backend'
        │  import type { Doc, Id } from '@canchero/backend'
        ▼
packages/backend/src/index.ts
        │  re-exports api, internal, Doc<T>, Id<T>
        ▼
packages/backend/convex/_generated/api.d.ts   ← generated by Convex CLI
packages/backend/convex/_generated/dataModel.d.ts  ← generated, typed from schema
        │
        │  source of truth for types
        ▼
packages/backend/convex/schema.ts   ← THIS CHANGE
```

After `schema.ts` is written:
1. Developer runs `npx convex dev` (or `pnpm --filter @canchero/backend dev`)
2. Convex CLI regenerates `_generated/api.d.ts` and `_generated/dataModel.d.ts`
3. `Doc<"reservas">`, `Id<"sedes">` etc. become fully typed throughout the monorepo

## Interfaces / Contracts

### Embedded object shapes (defined inline inside `defineTable`)

```ts
// HorarioDia — one entry per day of week
const horarioDia = v.object({
  dia: v.union(
    v.literal("lunes"), v.literal("martes"), v.literal("miercoles"),
    v.literal("jueves"), v.literal("viernes"), v.literal("sabado"),
    v.literal("domingo")
  ),
  abierto: v.boolean(),
  apertura: v.string(),   // "HH:MM" 24h
  cierre: v.string(),     // "HH:MM" 24h
})

// Feriado
const feriado = v.object({
  fecha: v.string(),   // ISO 8601 "YYYY-MM-DD"
  nombre: v.string(),
  cerrado: v.boolean(),
})

// PricingConfig
const pricingConfig = v.object({
  precioPorHora: v.number(),
  moneda: v.literal("ARS"),
  descuentoSocio: v.optional(v.number()),  // porcentaje 0-100
})

// CourtScheduleOverride (optional per Cancha)
const courtScheduleOverride = v.object({
  horarios: v.optional(v.array(horarioDia)),
  pricing: v.optional(pricingConfig),
})
```

### Table summary

| Table | Key fields | Indexes |
|-------|-----------|---------|
| `users` | `clerkId`, `role`, `email` | `by_clerk_id` (clerkId) |
| `sedeAccess` | `userId`, `sedeId`, `role` | `by_user_sede` (userId+sedeId), `by_sede` (sedeId) |
| `sedes` | `ownerId`, `nombre`, `horarios[]`, `feriados[]`, `pricing` | `by_owner` (ownerId) |
| `canchas` | `sedeId`, `nombre`, `tipo`, `override?` | `by_sede` (sedeId) |
| `reservas` | `canchaId`, `clienteId`, `fecha`, `horaInicio`, `horaFin`, `estado`, `seriesId?` | `by_cancha_fecha` (canchaId+fecha), `by_cliente` (clienteId), `by_series` (seriesId) |
| `payments` | `reservaId`, `monto`, `estado`, `mercadoPagoId?` | `by_reserva` (reservaId), `by_created_at` (\_creationTime) |
| `recurrenceSeries` | `canchaId`, `clienteId`, `regla`, `activa` | `by_cancha` (canchaId) |
| `clientes` | `sedeId`, `userId?`, `nombre`, `telefono` | `by_sede` (sedeId), `by_user` (userId) |

### Updated `src/index.ts`

```ts
export { api, internal } from '../convex/_generated/api'
export type { Doc, Id } from '../convex/_generated/dataModel'
```

This allows consumers to write:

```ts
import { api } from '@canchero/backend'
import type { Doc, Id } from '@canchero/backend'

type Reserva = Doc<"reservas">
type SedeId = Id<"sedes">
```

## Testing Strategy

| Layer | What to Test | Approach |
|-------|-------------|----------|
| Type-check | All 8 `Doc<T>` types resolve without `any` | `tsc --noEmit` after `npx convex dev` |
| Integration | Schema accepted by Convex local backend | `npx convex dev` exits without error |
| Compilation | `@canchero/backend` compiles in web + mobile | `turbo build` or `tsc -p` per app |

No unit tests — schema is declarative data, not logic. Testing is compile-time + Convex CLI acceptance.

---

## Migration / Rollout

No migration required. The backend has no live data and no existing schema.
Rollback = revert `schema.ts` commit + `npx convex dev` to regenerate `_generated/`.

## Open Questions

- [ ] `recurrenceSeries.regla`: store as RRULE string (RFC 5545) or as structured object? Structured is easier to query; RRULE is more standard. Decision deferred to functions layer — schema stores `v.string()` for now, can be narrowed later without a breaking schema migration.
- [ ] `payments.mercadoPagoId`: should this be a unique index? If yes, Convex enforces at DB level. Recommended yes — add `{ unique: true }` to the index when Convex supports it (currently unique enforcement is handled in mutation code, not schema).
