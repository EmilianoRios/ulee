### 2. Schema — All 8 Entities Present

The schema MUST define exactly these 8 tables. No other tables. All using Convex's `defineTable`.

#### 2.1 `users`

Represents any authenticated person in the system. Identity is managed by Clerk.

Required fields:
- `clerkId: v.string()` — Clerk user ID, globally unique
- `role: v.union(v.literal("admin"), v.literal("dueno"), v.literal("empleado"), v.literal("cliente"))` — system role
- `nombre: v.string()`
- `email: v.string()`

Optional fields:
- `avatarUrl: v.optional(v.string())`

Constraints:
- `clerkId` MUST be unique across the table (enforced via index)
- `role` MUST be one of the four literals — no freeform strings

#### 2.2 `sedeAccess`

Grants an `empleado` (or `dueno`) access to specific sedes. One record per (user, sede) pair.

Required fields:
- `userId: v.id("users")`
- `sedeId: v.id("sedes")`

Constraints:
- A `dueno` with a `sedeAccess` record has explicit access to that sede
- A user without any `sedeAccess` record for a given sede MUST be considered unauthorized for that sede (authorization logic is out of scope for this change, but the schema must support it)
- Combination of `(userId, sedeId)` MUST be unique — enforced via index

#### 2.3 `sedes`

Represents a physical sports venue. Owned by a `dueno`.

Required fields:
- `duenoid: v.id("users")` — the owner
- `nombre: v.string()`
- `direccion: v.string()`
- `telefono: v.string()`
- `horarios: v.object({...})` — embedded schedule config (see §3.1)
- `pricingConfig: v.object({...})` — embedded pricing defaults (see §3.2)

Optional fields:
- `descripcion: v.optional(v.string())`
- `logoUrl: v.optional(v.string())`
- `feriados: v.optional(v.array(v.string()))` — ISO date strings ("YYYY-MM-DD") of days the sede is closed

Constraints:
- `horarios` and `pricingConfig` MUST be embedded objects (not separate tables)
- Embedded objects MUST be flat (maximum 1 level of nesting inside the object)
- `feriados` is optional and defaults to empty / absent (not required at creation)

#### 2.4 `canchas`

Represents a single court within a sede. Prices and schedules are overrides on top of the sede defaults.

Required fields:
- `sedeId: v.id("sedes")`
- `nome: v.string()` — e.g., "Cancha 1", "Cancha Techada"
- `deporte: v.string()` — e.g., "padel", "futbol5", "tenis"
- `status: v.union(v.literal("activa"), v.literal("inactiva"), v.literal("mantenimiento"))`

Optional fields:
- `descripcion: v.optional(v.string())`
- `precioOverride: v.optional(v.number())` — overrides `pricingConfig.precioPorHora` from the sede
- `horarioOverride: v.optional(v.object({...}))` — overrides sede `horarios` for this specific court (same shape as §3.1)

Constraints:
- `status` transitions independently of any reservation blocks; a maintenance reservation does not automatically set `status = "mantenimiento"` and vice versa
- When `precioOverride` is absent, the applicable price is `sede.pricingConfig.precioPorHora`
- When `horarioOverride` is absent, the applicable schedule is `sede.horarios`

#### 2.5 `reservas`

Represents a single time-slot booking on a court. May belong to a recurrence series.

Required fields:
- `canchaId: v.id("canchas")`
- `sedeId: v.id("sedes")` — denormalized for efficient sede-level queries
- `fecha: v.string()` — ISO date "YYYY-MM-DD"
- `horaInicio: v.string()` — "HH:MM" 24-hour format
- `horaFin: v.string()` — "HH:MM" 24-hour format
- `status: v.union(v.literal("pendiente"), v.literal("confirmada"), v.literal("cancelada"), v.literal("completada"))`
- `origen: v.union(v.literal("web"), v.literal("mobile"), v.literal("manual"))` — who/what created it

Optional fields:
- `clienteId: v.optional(v.id("clientes"))` — set when booked by or for a registered cliente
- `seriesId: v.optional(v.id("recurrenceSeries"))` — set when part of a recurring series
- `notas: v.optional(v.string())`
- `precioTotal: v.optional(v.number())` — captured at booking time, not derived at query time

Constraints:
- `sedeId` MUST match the `sedeId` of the referenced `canchaId` (consistency, validated at mutation time — out of scope for schema but MUST be enforced in functions)
- `fecha` + `horaInicio` + `horaFin` together define the time slot; no overlap enforcement at schema level (enforced at mutation level)
- Cancelling a reserva (setting `status = "cancelada"`) MUST NOT modify its `seriesId` or the `RecurrenceSeries` document
- A reserva with `origen = "manual"` represents a block created by staff (maintenance, personal use) — MAY have `clienteId = null`

#### 2.6 `payments`

Records a single payment transaction associated with a reserva. Multiple payments can exist per reserva (e.g., seña + saldo).

Required fields:
- `reservaId: v.id("reservas")`
- `sedeId: v.id("sedes")` — denormalized for sede-level payment queries
- `monto: v.number()` — amount in ARS cents (integer) or pesos (float) — MUST pick one and document the choice inline
- `tipo: v.union(v.literal("sena"), v.literal("saldo"), v.literal("total"))` — seña = deposit, saldo = remainder, total = full payment
- `metodo: v.union(v.literal("efectivo"), v.literal("transferencia"), v.literal("mercadopago"))` — payment channel
- `status: v.union(v.literal("pendiente"), v.literal("acreditado"), v.literal("rechazado"), v.literal("devuelto"))`

Optional fields:
- `mpPaymentId: v.optional(v.string())` — MercadoPago transaction ID, set when `metodo = "mercadopago"`
- `notas: v.optional(v.string())`

Constraints:
- `mpPaymentId` MUST be present when `metodo = "mercadopago"` (enforced at mutation level, not schema level)
- Recording a seña and a saldo are two independent `Payment` documents linked to the same `reservaId`

#### 2.7 `recurrenceSeries`

Defines the recurrence rule for a set of repeating reservations. The series itself does not hold time slots — individual `Reserva` documents do.

Required fields:
- `sedeId: v.id("sedes")`
- `canchaId: v.id("canchas")`
- `frecuencia: v.union(v.literal("semanal"), v.literal("quincenal"))` — recurrence frequency
- `diaSemana: v.number()` — 0 = Sunday … 6 = Saturday (ISO-like, matches JS `Date.getDay()`)
- `horaInicio: v.string()` — "HH:MM"
- `horaFin: v.string()` — "HH:MM"
- `fechaInicio: v.string()` — ISO date "YYYY-MM-DD"
- `status: v.union(v.literal("activa"), v.literal("cancelada"), v.literal("completada"))`

Optional fields:
- `clienteId: v.optional(v.id("clientes"))`
- `fechaFin: v.optional(v.string())` — ISO date; absent means open-ended
- `notas: v.optional(v.string())`

Constraints:
- Cancelling a `RecurrenceSeries` (setting `status = "cancelada"`) MUST NOT automatically cancel individual `Reserva` instances — that is a separate mutation concern
- Cancelling a single `Reserva` in the series MUST NOT modify the `RecurrenceSeries` document
- Future `Reserva` instances not yet created at the time of series cancellation MUST NOT be generated (enforcement at mutation level)

#### 2.8 `clientes`

Represents a customer scoped to a single sede. A person who visits two sedes has two independent `Cliente` records.

Required fields:
- `sedeId: v.id("sedes")` — scope boundary
- `nome: v.string()`
- `telefono: v.string()`

Optional fields:
- `email: v.optional(v.string())`
- `clerkId: v.optional(v.string())` — set if the cliente registers via the mobile app; links to a `users` record
- `notas: v.optional(v.string())`

Constraints:
- `clerkId` being absent means the cliente was created manually by staff (walk-in or phone)
- Two `Cliente` records with the same `clerkId` but different `sedeId` are valid and expected
- Cross-sede data (e.g., booking history at another sede) MUST NOT be derivable from a single `Cliente` record

### 3. Embedded Config Objects

#### 3.1 `HorarioConfig` shape (used in `sedes.horarios` and `canchas.horarioOverride`)

```
{
  diasHabiles: v.array(v.number()),   // 0–6, days the venue/court operates
  apertura: v.string(),               // "HH:MM" opening time
  cierre: v.string(),                 // "HH:MM" closing time
}
```

Constraints:
- `diasHabiles` array MUST contain values 0–6 only
- `apertura` and `cierre` MUST be "HH:MM" 24-hour strings
- This shape is used identically in both `Sede.horarios` and `Cancha.horarioOverride`

#### 3.2 `PricingConfig` shape (used in `sedes.pricingConfig`)

```
{
  precioPorHora: v.number(),                        // base price per hour
  moneda: v.literal("ARS"),                         // currency, ARS only for now
  porcentajeSena: v.optional(v.number()),           // 0–100, deposit percentage
}
```

Constraints:
- `precioPorHora` MUST be a positive number
- `moneda` MUST be `"ARS"` — no other currency is in scope
- `porcentajeSena` is optional; when absent, the system treats deposit as 0 (no deposit required)
- This object lives only in `Sede` — `Cancha` overrides price via a flat `precioOverride` number, not a full `PricingConfig`

### 4. Index Requirements

The following indexes MUST be defined. Queries without a matching index are not acceptable.

| Table | Index Name | Fields | Justification |
|-------|------------|--------|---------------|
| `users` | `by_clerkId` | `[clerkId]` | Auth lookup on every request |
| `sedeAccess` | `by_userId` | `[userId]` | Load all sedes a user can access |
| `sedeAccess` | `by_sedeId` | `[sedeId]` | Load all users who have access to a sede |
| `sedeAccess` | `by_userId_sedeId` | `[userId, sedeId]` | Uniqueness check + direct permission lookup |
| `sedes` | `by_duenoid` | `[duenoid]` | Load all sedes owned by a dueno |
| `canchas` | `by_sedeId` | `[sedeId]` | Load all courts of a sede |
| `reservas` | `by_sedeId` | `[sedeId]` | Sede-level calendar view |
| `reservas` | `by_canchaId_fecha` | `[canchaId, fecha]` | Availability check for a specific court on a date |
| `reservas` | `by_clienteId` | `[clienteId]` | Load all reservations for a client |
| `reservas` | `by_seriesId` | `[seriesId]` | Load all instances of a recurring series |
| `payments` | `by_reservaId` | `[reservaId]` | Load all payments for a reservation |
| `payments` | `by_sedeId` | `[sedeId]` | Sede-level payment reporting |
| `recurrenceSeries` | `by_sedeId` | `[sedeId]` | Load all series for a sede |
| `recurrenceSeries` | `by_canchaId` | `[canchaId]` | Load all series for a court |
| `clientes` | `by_sedeId` | `[sedeId]` | Load all clients of a sede |
| `clientes` | `by_clerkId` | `[clerkId]` | Link a Clerk-registered user to their cliente profile |

### 5. Type Exports

`packages/backend/src/index.ts` MUST export:
- `api` and `internal` from `_generated/api` (already present)
- Inferred document types using Convex's `Doc<"tableName">` pattern, one export per table:
  - `UserDoc` → `Doc<"users">`
  - `SedeAccessDoc` → `Doc<"sedeAccess">`
  - `SedeDoc` → `Doc<"sedes">`
  - `CanchaDoc` → `Doc<"canchas">`
  - `ReservaDoc` → `Doc<"reservas">`
  - `PaymentDoc` → `Doc<"payments">`
  - `RecurrenceSeriesDoc` → `Doc<"recurrenceSeries">`
  - `ClienteDoc` → `Doc<"clientes">`
- Inferred ID types using Convex's `Id<"tableName">` pattern:
  - `SedeId` → `Id<"sedes">`
  - `CanchaId` → `Id<"canchas">`
  - `ReservaId` → `Id<"reservas">`
  - `ClienteId` → `Id<"clientes">`
- The embedded config types exported as plain TypeScript interfaces:
  - `HorarioConfig`
  - `PricingConfig`

Constraints:
- All exports MUST be named exports (no default exports)
- Apps (`apps/web`, `apps/mobile`) MUST be able to import any of these via `import { ... } from "@canchero/backend"` with no TypeScript errors
- No app MUST ever import directly from `../convex/_generated/...`

### 6. Inline Documentation

`schema.ts` MUST include inline comments for:
- Why `Payment` is a separate table (MercadoPago reconciliation)
- Why `Cliente` is scoped per `Sede` (data isolation between sedes)
- The override model for `Cancha` (sede base, cancha overrides price/schedule)
- Why `RecurrenceSeries` is independent from `Reserva` instances (cancellation isolation)

## Acceptance Scenarios

### Scenario 1 — A dueño creates a Sede with full config

```
Given: a User with role "dueno" exists (id: dueno1)
When:  a "sedes" document is created with:
         duenoid = dueno1
         nome = "Padel Club Norte"
         horarios = { diasHabiles: [1,2,3,4,5], apertura: "08:00", cierre: "22:00" }
         pricingConfig = { precioPorHora: 3500, moneda: "ARS", porcentajeSena: 30 }
         feriados = ["2026-07-09"]
Then:  the document is persisted with all fields intact
 And:  querying by_duenoid(dueno1) returns this sede
 And:  the TypeScript type of the document matches SedeDoc
```

### Scenario 2 — A Cancha with a price override is added to a Sede

```
Given: a Sede "sedes/abc" with pricingConfig.precioPorHora = 3500
When:  a "canchas" document is created with:
         sedeId = "sedes/abc"
         nome = "Cancha Techada"
         deporte = "padel"
         status = "activa"
         precioOverride = 4500
Then:  the document is persisted
 And:  querying by_sedeId("sedes/abc") returns this cancha
 And:  the applicable price for this cancha is 4500 (override takes precedence)
 And:  otro cancha in the same sede without precioOverride has applicable price 3500
```

### Scenario 3 — A dueño/empleado creates a Reserva from the web dashboard

```
Given: a Cancha "canchas/xyz" in Sede "sedes/abc" exists with status "activa"
  And: no other Reserva exists for canchas/xyz on fecha "2026-06-15" between 10:00 and 11:00
When:  a "reservas" document is created with:
         canchaId = "canchas/xyz"
         sedeId = "sedes/abc"
         fecha = "2026-06-15"
         horaInicio = "10:00"
         horaFin = "11:00"
         status = "confirmada"
         origen = "web"
Then:  the document is persisted
 And:  querying by_canchaId_fecha("canchas/xyz", "2026-06-15") returns this reserva
 And:  the reserva has no seriesId (it is a one-off booking)
```

```
         sedeId = "sedes/abc"
         fecha = "2026-06-20"
         horaInicio = "18:00"
         horaFin = "19:00"
         status = "pendiente"
         origen = "mobile"
         clienteId = "clientes/cli1"
Then:  the document is persisted
 And:  querying by_clienteId("clientes/cli1") returns this reserva
 And:  querying by_canchaId_fecha("canchas/xyz", "2026-06-20") returns this reserva
```

### Scenario 5 — A RecurrenceSeries generates individual Reserva instances

```
Given: a RecurrenceSeries is created:
         sedeId = "sedes/abc"
         canchaId = "canchas/xyz"
         frecuencia = "semanal"
         diaSemana = 3 (Wednesday)
         horaInicio = "20:00"
         horaFin = "21:00"
         fechaInicio = "2026-06-04"
         status = "activa"
When:  4 weekly Reserva documents are created (2026-06-04, 11, 18, 25):
         each with seriesId pointing to this RecurrenceSeries
Then:  querying by_seriesId(series.id) returns exactly 4 reserva documents
 And:  each reserva has its own independent _id, fecha, status
 And:  the RecurrenceSeries document is NOT modified by the creation of reservas
```

### Scenario 6 — One instance of a series is cancelled without affecting the series

```
Given: a RecurrenceSeries with status "activa" (id: series1)
  And: 4 Reserva documents with seriesId = series1
When:  reserva[2] (2026-06-18) has its status set to "cancelada"
Then:  reserva[2].status = "cancelada"
 And:  reserva[1].status remains "confirmada"
 And:  reserva[3].status remains "confirmada"
 And:  reserva[4].status remains "confirmada"
 And:  series1.status remains "activa"
 And:  reserva[2].seriesId still equals series1 (seriesId is NOT cleared on cancel)
```

```
Given: a Reserva "reservas/r1" with precioTotal = 4000
```

### Scenario 8 — SedeAccess grants an empleado access to specific sedes

```
Given: a User with role "empleado" (id: emp1)
  And: two Sedes exist: "sedes/s1" and "sedes/s2"
When:  a single SedeAccess document is created:

         sedeId = "sedes/s1"
Then:  querying by_userId(emp1) returns 1 SedeAccess document (for s1 only)
 And:  querying by_sedeId("sedes/s1") returns emp1 in the results
```

### Scenario 9 — Cancha.status changes independently of maintenance reservation blocks

```
Given: a Cancha "canchas/xyz" with status "activa"
  And: a Reserva exists with:

         notas = "Mantenimiento preventivo"

Then:  canchas/xyz.status = "mantenimiento"
 And:  the maintenance Reserva document is NOT modified
 And:  querying by_sedeId for reservas still returns the manual reserva
 And:  no cascade update occurs — status transitions are independent mutations
```

## Out of Scope (Spec Boundary)

The following are explicitly NOT part of this spec:

- Convex query or mutation function implementations
- Overlap validation logic for reserva time slots
- Authorization enforcement (which role can access which sede)
- MercadoPago webhook handling and `mpPaymentId` validation
- Freemium / Premium plan limits
- Client rating or loyalty fields
- Statistics or reporting queries

---

## Assumptions Made

1. **Currency unit**: `monto` in `Payment` is stored as a plain float in ARS pesos (not cents). The inline comment in schema.ts MUST document this choice explicitly.
2. **`diaSemana` encoding**: uses JS `Date.getDay()` convention (0 = Sunday, 6 = Saturday). Documented inline.
3. **`fecha` format**: ISO string "YYYY-MM-DD" for all date-only fields. Timezone is always Argentina (UTC-3); functions are responsible for conversion but the schema stores the string.
4. **`clientes.by_clerkId` index**: defined on `clientes` even though `clerkId` is optional, because it is the primary cross-reference for mobile-registered users.
5. **No `users` record is created by schema**: the `users` table is populated by a Clerk webhook handler (out of scope); the schema only defines the shape.
